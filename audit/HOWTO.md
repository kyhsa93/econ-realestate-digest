# 자동 점검 사양서

매일 한 번, 이 저장소를 **로컬에서 직접 돌려 보고** 고칠 값이 있는 것만 GitHub 이슈로
올린다. 이 문서가 사양이다 — 부르는 스크립트의 프롬프트가 아니라 이 파일을 따른다.

## 이 작업이 실패하는 방식

먼저 이것부터. 매일 도는 이슈 봇이 망가지는 길은 하나뿐이고, 그건 **매일 뭔가를
올리는 것**이다. 스무 개쯤 쌓이면 사람은 목록을 안 읽고, 그 순간 진짜 하나가 섞여
있어도 같이 묻힌다. 그래서 규칙의 절반이 "올리지 마라"다.

**0건으로 끝나는 날이 정상이다.** 하루 최대 3건이되, 3건은 상한이지 목표가 아니다.

## 무엇을 보는가

두 갈래다. 둘 다 봐도 되고, 한쪽만 나와도 된다.

### 1. 오류

돌아가지 않거나, 틀린 값을 보여주거나, 조용히 깨진 것.

### 2. 사업성·상품성

**이 사이트의 지금 목표는 애드센스 재신청 통과와 검색 유입이다.** 애드센스는 한 번
"가치가 별로 없는 콘텐츠"로 반려했다. 그래서 값이 되는 제안은 대체로 이 셋 중 하나다.

- 사람이 읽을 것이 늘어나는가 (자동 생성 틀을 반복하는 것 말고)
- 검색에서 찾아지는 자리가 생기는가 (대형 사이트가 페이지로 안 만드는 형태)
- 이미 있는 데이터에서 아직 안 보여주고 있는 것이 있는가

## 반드시 지킬 것

**질문하지 마라.** 이 작업은 헤드리스로 돈다 — 답할 사람이 없다. 물어보고 멈추면
아무것도 안 한 것이고, 찾아 놓은 것까지 같이 버려진다. 판단이 서지 않으면 두 길뿐이다:
근거가 충분하면 올리고, 부족하면 올리지 않기로 정하고 왜 안 올렸는지 보고한다.

**동시 실행은 걱정하지 마라.** 부르는 스크립트가 `flock`으로 막고 있어서 감사는 한
번에 하나만 돈다. 프로세스 목록에서 `daily_audit.sh`나 `claude -p`가 보이면 그건
너 자신이다 — 다른 감사가 도는지 확인하려 들지 마라. 실제로 첫 실행에서 자기 자신을
보고 "중복될까 봐" 물어보며 멈춘 적이 있다.

**전부 로컬에서 확인한다.** 추측으로 이슈를 쓰지 마라. 모든 주장에는 실제로 실행한
명령과 그 출력이 붙어야 한다. 명령 없이 쓴 문장은 이슈에 넣지 마라.

**중복을 먼저 확인한다.** `gh issue list --state all --limit 100` 을 **가장 먼저**
실행한다. 열린 것뿐 아니라 **닫힌 것도** 본다 — 닫혔다는 것은 사람이 이미 판단했다는
뜻이고, 같은 것을 다시 올리는 것은 그 판단을 무시하는 것이다.

**하루가 아니라 며칠을 본다.** 데이터가 오늘만 이상한 것은 이슈가 아니다. 국토부
응답이 하루 비는 것, 신고가 덜 찬 주가 낮게 나오는 것은 설계상 정상이다
(`docs/method.html` 참고). **사흘 이상 이어지거나, 반복되는 것만** 올린다.

**한 번에 하나씩.** 이슈 하나에 문제 하나. "이것저것 개선" 같은 이슈는 아무도 못 닫는다.

## 올리지 말 것

- **테스트가 이미 막고 있는 것.** `npm test`가 잡아 주는 것을 이슈로 올리면 소음이다.
  깨졌다면 그건 이슈가 아니라 지금 고칠 일이고, 이 봇은 코드를 고치지 않는다 —
  깨진 사실만 한 건으로 올린다.
- **근거 없는 취향.** "리팩터링하면 좋겠다", "더 예쁘게" 류. 중복 코드를 올리려면
  그 중복 때문에 실제로 생긴 사고를 대라.
- **사이트가 안 하기로 한 것.** 집값 전망, 특정 단지·지역 추천, 유료 등재.
  `docs/method.html`의 "하지 않는 것"에 적혀 있다. 제안하지 마라.
- **큰 재작성.** 프레임워크 교체, 전면 재설계. 이 저장소는 서버가 없는 정적 사이트이고
  그게 설계다.
- **자동 생성 페이지를 늘리자는 제안** 그 자체. 페이지 수를 늘리는 것이 아니라 페이지가
  서로 다른 이야기를 하게 만드는 것이 이 사이트가 반려에서 배운 것이다
  (`scripts/district-facts.mjs` 주석 참고).

## 절차

1. `gh issue list --state all --limit 100` — 이미 있는 것을 먼저 안다
2. `git log --oneline -20` — 최근에 무엇이 바뀌었나
3. `npm ci` (또는 `npm install`) 후 `npm test` — 통과하는가
4. 생성물이 소스와 맞는가:
   `node scripts/build-realestate-pages.mjs && node scripts/build-budget-pages.mjs && node scripts/build-news-pages.mjs && node scripts/build-rate-pages.mjs`
   실행 뒤 `git status --porcelain docs`가 비어야 한다
5. 데이터 상태:
   - `docs/data/*.json`의 `updatedAt`이 얼마나 묵었나 (전부 하루 1회 갱신이다)
   - `docs/data/realestate.json`에서 표본이 얇아 값을 비운 자치구가 몇이나 되나
   - `docs/data/realestate-trend.json`에서 주간 변동이 비정상적으로 큰 자치구
   - 예산대별 거래 건수(`docs/data/budget-deals.json`)가 0에 가까운 밴드
6. 필요하면 실제 페이지를 열어 본다 (WebFetch로 `https://kyhsa93.github.io/jipgye/`)
7. 위에서 나온 것 중 **올릴 값이 있는 것만** 이슈로 만든다

## 이슈 형식

제목은 무엇이 문제인지 한 줄. `[오류]` 또는 `[개선]`으로 시작한다.

본문:

```markdown
## 무엇이

(한두 문장. 무엇이 어떻게 잘못됐거나 무엇이 없는가.)

## 확인한 것

```
$ 실제로 실행한 명령
실제 출력
```

(명령과 출력을 그대로. 이게 이 이슈의 근거다.)

## 왜 값이 있나

(고치면 무엇이 나아지는가. 오류면 누가 무엇을 잘못 보게 되는지, 개선이면
위 "사업성·상품성" 셋 중 어디에 걸리는지.)

## 제안

(구체적으로. 파일 이름과 손댈 자리까지. 확신이 없으면 "확인 필요"라고 쓴다.)

## 고쳐졌는지 확인하는 법

(어떤 명령이 어떻게 나오면 닫아도 되는가.)
```

라벨: 오류는 `bug`, 개선은 `enhancement`. 둘 다 `audit`을 같이 단다.

## 하지 말 것

- **커밋하지 마라. push하지 마라. 파일을 고치지 마라.** 이 봇이 저장소에 남기는 것은
  이슈뿐이다. 고치는 것은 사람이 한다.
- `npm test`가 깨졌다고 코드를 고치지 마라. 깨진 사실을 이슈로 올리고 끝낸다.
- 올릴 것이 없으면 아무것도 하지 마라. 억지로 채우지 마라.
